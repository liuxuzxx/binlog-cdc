# 序列化格式对比：体积、序列化速度与反序列化速度

网络通信中的序列化，是把对象转换成可传输或可存储的字节。反序列化则执行相反的过程，把字节还原成对象。

评价一种序列化方式，通常要看三个直接指标：

1. 编码后的数据占用多少字节；
2. 序列化需要多长时间；
3. 反序列化需要多长时间。

如果只讨论数据体积，优化主要集中在两个地方：字段名和字段值。

```text
字段名优化：减少字段名在每条消息中的重复传输
字段值优化：用更紧凑的二进制方式表达数字、布尔值等数据
综合优化：同时减少字段名和字段值的占用
```

XML、JSON、MessagePack 和 Protobuf 的主要差别，就在于它们对字段名和字段值采用了不同的编码方式。本文使用同一条 `UserInfo` 数据进行说明。

## 一、测试数据

```json
{
  "id": 100426,
  "username": "alice",
  "email": "alice@example.com",
  "phone": "00000000000",
  "age": 30,
  "score": 98.5,
  "vip": true,
  "created_at": 1787307796,
  "address": {
    "city": "Guangzhou",
    "zip": "510000"
  },
  "tags": ["rust", "kafka", "cdc"]
}
```

把所有字段值按文本形式计算，这条数据的值共占 86 字节。不同格式在本机测试中的编码结果如下：

| 编码格式 | 实测大小 | 相对 86 字节值数据增加的空间 |
|---|---:|---:|
| XML | 308 字节 | 222 字节 |
| JSON | 215 字节 | 129 字节 |
| Protobuf | 101 字节 | 15 字节 |

这里的 86 字节只是便于理解的文本基线，并不是所有二进制格式都必须达到的下限。例如整数转换成二进制后，可能比它的十进制文本更短；`double` 等定长类型也可能比对应的短文本更长。最终大小应以实际编码结果为准。

## 二、字段名如何影响数据体积

### 1. XML：每个字段名出现两次

```xml
<username>alice</username>
```

`username` 同时出现在开始标签和结束标签中。只计算标签，一个长度为 `N` 的字段名需要 `2N + 5` 个字符：

```text
<name>   = N + 2
</name>  = N + 3
```

XML 的结构清楚，但标签会带来较高的重复开销。

### 2. JSON：每个字段名出现一次

```json
"username":"alice"
```

JSON 不需要结束标签，字段名只出现一次。与 XML 相比，它减少了重复的字段名和标签字符，因此同一份数据通常更小，解析规则也更简单。

把字段名缩短也能继续减少体积。例如，把 `created_at` 改成 `t`，每条消息都会少传几个字符。不过这种做法会降低可读性，并且无法减少字段值本身的占用。

### 3. Protobuf：线上只传字段编号

```protobuf
message UserInfo {
  int64 id = 1;
  string username = 2;
  int64 created_at = 8;
}
```

字段名保存在 `.proto` schema 中，通信时只传字段编号和 wire type。对于编号较小的常见字段，这部分通常只占 1 字节。

```text
08 ca 90 06       # 字段 1，后面是 id 的 varint 值
12 05 616c696365  # 字段 2，长度为 5，值为 alice
```

Protobuf 用双方预先共享的 schema 换取更小的传输体积。字段名无论多长，都不会在每条消息中重复发送。

### 4. CSV 和数组：用位置表达含义

CSV 可以只在表头发送一次字段名，后续各行按列的位置解释数据。二进制数组还可以省略表头，直接约定每个位置的含义。

这种方式的字段名开销很低，但结构变更需要更加谨慎。增加、删除或调整字段顺序时，发送方和接收方必须遵守同一份位置约定。

## 三、字段值如何影响数据体积

### 1. 文本格式需要把数字转换成字符

在 JSON 和 XML 中，整数 `100426` 需要用 6 个字符表示。它的二进制有效位数是 17 位，使用普通二进制整数编码时，3 个字节就能容纳该值。

时间戳 `1787307796` 的十进制文本占 10 字节，而 32 位无符号整数可用 4 字节表示。文本格式的优势是可直接阅读，代价是数值转换和额外空间。

### 2. Protobuf 使用二进制和变长整数

Protobuf 主要通过以下方式紧凑编码字段值：

- 整数直接按二进制编码，不需要先转换成十进制字符串；
- `varint` 每个字节使用 7 位保存数据，小整数占用的字节更少；
- proto3 的非 optional 标量默认值通常不会写入消息。

例如，`age=30` 使用 varint 只需要 1 字节。对于大量小整数、布尔值和默认值字段，二进制编码的体积优势会更明显。

默认值省略也会带来语义约束。如果业务必须区分“字段未设置”和“字段明确设置为 0”，应使用 proto3 的 `optional`、wrapper 类型或独立的业务状态字段表达，不能只依赖标量默认值。

### 3. MessagePack 和 BSON：保留字段名，二进制编码字段值

MessagePack、BSON 等格式仍会在消息中携带字段名，但会用二进制类型表达数字、布尔值、字符串和集合。它们通常比 JSON 更紧凑，也省去了部分文本到数值的转换。

由于字段名仍然随每条消息发送，当对象字段较多或字段名较长时，这部分开销依然存在。

## 四、Protobuf 为什么更小

在这次测试中，Protobuf 同时减少了字段名和部分字段值的占用：

| 字段 | 文本值大小 | 字段标记 | Protobuf 值编码 | 合计 |
|---|---:|---:|---:|---:|
| `id=100426` | 6 | 1 | 3（varint） | 4 |
| `username=example_user` | 5 | 1 | 1 字节长度前缀 + 5 | 7 |
| `email=alice@...` | 17 | 1 | 1 字节长度前缀 + 17 | 19 |
| `created_at=1787307796` | 10 | 1 | 5（varint） | 6 |
| `age=30` | 2 | 1 | 1（varint） | 2 |
| `score=98.5` | 4 | 1 | 8（double） | 9 |
| `vip=true` | 4 | 1 | 1 | 2 |
| `phone`、`address`、`tags` | 其余部分 |  |  | 52 |
| 合计 | 86 |  |  | 101 |

三种格式的差异可以概括为：

```text
XML：字段名在开始和结束标签中重复，字段值使用文本表示
JSON：字段名只出现一次，字段值仍以文本为主
Protobuf：字段名转换为编号，字段值使用二进制、varint 和默认值省略
```

因此，Protobuf 在字段多、消息量大、数值字段较多的机器间通信中，通常更容易获得较小的消息体。

## 五、格式对比

| 格式 | 字段名处理 | 字段值处理 | 本次实测大小 | 主要特点 |
|---|---|---|---:|---|
| XML | 开始和结束标签重复字段名 | 文本 | 308 字节 | 可读性高，结构开销较大 |
| JSON | 每个字段名出现一次 | 文本为主 | 215 字节 | 通用性和可读性好 |
| 短字段名 JSON | 缩短字段名 | 文本为主 | 约 180 字节 | 体积下降，但可读性变差 |
| MessagePack | 仍携带字段名 | 二进制 | 约 170 字节 | 无需独立 schema，数值编码更紧凑 |
| CSV/数组 | 表头一次或按位置约定 | 文本或二进制 | 取决于行数和实现 | 适合同构、结构稳定的数据 |
| Protobuf | schema 保存字段名，消息携带编号 | 二进制、varint、默认值省略 | 101 字节 | 体积小，需要维护 schema |

表中的大小来自当前 `UserInfo` 样本和本机测试。不同语言、序列化库、字段分布和批量大小都会影响结果，不能把单个样本直接当成所有场景的性能结论。

## 六、binlog-cdc 场景中的选择

假设 Rust 服务从 MySQL 读取用户变更，发送给 Java 服务处理，结果还要写入 Kafka 供其他系统消费：

```text
┌────────────┐   高频内部通信   ┌────────────┐
│ Rust CDC   │ ───────────────▶ │ Java 服务  │
└────────────┘                  └────────────┘
       │                               │
       └──────── 写入 Kafka ───────────┘
                    │
                    ▼
          Java / Python / 命令行消费者
```

不同链路的约束并不相同：

| 链路 | 主要约束 | 更适合的方向 |
|---|---|---|
| Rust CDC → Java 服务 | 调用量大，双方都能维护 schema | 优先评估 Protobuf 等 schema 驱动的二进制格式 |
| Java 内部服务通信 | 服务可统一升级，重视吞吐和延迟 | 优先评估二进制格式，并通过基准测试确认收益 |
| Kafka → 多语言或人工消费者 | 消费端多样，需要直接查看消息 | JSON 更容易接入和排查问题 |

如果按本次样本估算，每条消息从 JSON 的 215 字节降到 Protobuf 的 101 字节，1 亿条消息的原始编码体积相差约 11.4 GB。这个数字只表示消息体差值，不包含 Kafka、TCP、HTTP、TLS 等协议开销，也不能直接等同于最终网络流量或存储节省。

### 配置字段名映射

Rust 标识符不能直接使用 `scan.startup.mode` 这类带点号的配置名。JSON 或 YAML 可以通过 `#[serde(rename)]` 建立字段映射：

```rust
#[serde(rename = "scan.startup.mode")]
scan_startup_mode: String,
```

Protobuf 在线上只传字段编号，但生成代码中的字段名仍需符合目标语言规范。外部名称、代码字段名和 schema 编号之间的映射，应在接口定义中固定下来。

### 多态消息

同一个 Kafka topic 可能同时承载 `UserRisk` 和 `UserTag`。JSON 通常增加 `type` 字段进行区分；Protobuf 可以使用 `oneof` 或 envelope 消息，通过字段编号识别具体类型。

两种方式都需要稳定的类型标识和兼容性规则。区别在于 JSON 传输字符串类型名，Protobuf 传输字段编号。

### 默认值语义

如果 Java 端需要区分 `age=0` 和 `age` 未设置，协议定义必须明确这种差别。Protobuf 的默认值省略能够减小体积，但不能代替业务语义设计。

## 七、优化趋势和实施方向

序列化优化的目标可以归纳为三点：占用更小、序列化更快、反序列化更快。实际优化时应按以下顺序推进。

### 1. 先减少不必要的数据

- 只传接收方需要的字段；
- 避免在消息中重复携带可以从上下文获取的数据；
- 对批量消息复用公共元数据。

减少字段数量通常能同时改善体积和编解码速度。

### 2. 根据链路选择文本格式或二进制格式

需要人工阅读、临时调试或面对未知消费者时，JSON 的接入成本更低。服务内部高频通信、存储量大且双方能共享 schema 时，可以优先测试 Protobuf、MessagePack 等二进制格式。

### 3. 优化字段值编码

- 小整数优先使用 varint；
- 固定宽度数值根据取值范围选择合适类型；
- 明确默认值和字段缺失的业务语义；
- 避免把数值、布尔值和时间戳重复转换成字符串。

### 4. 降低序列化过程中的内存分配

序列化速度不仅取决于格式，也取决于实现。复用缓冲区、预估容量、减少中间字符串和对象复制，通常能同时降低 CPU 时间和 GC 压力。

### 5. 用真实数据做基准测试

比较格式时，应使用生产数据中常见的字段数量、字符串长度、默认值比例和批量大小。至少记录以下指标：

```text
encoded_bytes       编码后的字节数
serialize_ns/op     单次序列化耗时
deserialize_ns/op   单次反序列化耗时
allocations/op      单次操作的内存分配次数
bytes_allocated/op  单次操作分配的内存大小
```

还应区分单条消息和批量消息、冷启动和稳定运行。只有在同一数据集、同一硬件和相同测试条件下，结果才具有可比性。

## 八、结论

不同序列化格式没有脱离场景的统一最优解：

- XML 和 JSON 保留字段名，便于阅读和跨系统接入；
- MessagePack 等格式保留自描述结构，同时对字段值进行二进制编码；
- Protobuf 用 schema 和字段编号减少重复信息，适合结构稳定的高频服务通信；

判断一种格式为什么更节省，可以先看它是否减少了字段名，再看它如何编码字段值。最终选型还要同时比较编码体积、序列化耗时和反序列化耗时，并以真实业务数据的基准测试结果为准。

> 文中的编码大小来自本机样本测试。Protobuf 的结果可根据字段编号、wire type、varint 和长度前缀逐项核对，也可以使用 `protoc --encode` 复算。
